# Search benchmark

Generated by `scripts/bench_search.py` on 2026-11-25 (Windows AMD64 laptop, PostgreSQL 16.15 + pgvector 0.8.7 in Docker, shared with the dev stack).

- **Data:** 100,000 chunks in one embedding space, 5,000 documents. The vectors are 1024-dim projections of a 48-dim latent plus noise (real embeddings also have a low intrinsic dimension). Each text is 60 Zipf-distributed words from a 3,000-word vocabulary.
- **Load:** 51 s. Serial HNSW build (m=16, ef_construction=64): 272 s.
- **Queries:** 50 per row. Latency is end-to-end service time for a 25-hit page (SQL, fusion and snippets), excluding the query-embedding call.

## Latency (ms)

| mode | p50 | p95 | n |
|---|---:|---:|---:|
| keyword | 18.0 | 24.3 | 50 |
| semantic | 95.9 | 118.4 | 50 |
| semantic + filter (currency, ~1/3 of rows) | 160.2 | 191.3 | 50 |
| hybrid | 105.6 | 131.5 | 50 |

The query-embedding call is not in these numbers. It is a network call to the provider (hundreds of ms on the free tier) and is cached in Redis per (normalized query, space), so a repeated query skips it.

## HNSW recall@10 vs exact search

Exact = the same query with index scans disabled (sequential scan, the true top 10).

| hnsw.ef_search | recall@10 | p50 ms | p95 ms |
|---:|---:|---:|---:|
| 40 | 0.930 | 61.7 | 149.3 |
| 100 | 0.968 | 67.5 | 153.9 |
| 200 | 0.990 | 70.6 | 94.4 |

Recall changes by +0.038 from ef_search 40 to 100 and by +0.022 from 100 to 200. SEARCH_EF=100 is the default.
